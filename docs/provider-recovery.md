## 失敗の区別

| 失敗 | 自動処理 |
| --- | --- |
| 必須の画像解析の429、500/502/503等 | 全体で初回を含め最大3回。1回目の後は60秒、2回目の後は120秒を基準に0〜15秒のjitterを加える。SDKのRetryInfoが長ければそれを尊重。900秒超の指示では自動再試行を止める |
| 通信切断、Abort/timeout、HTTP408/504 | 外部処理の成否が不明なので自動再試行しない。新規の追跡済み予約枠を返却し、5分間新規受付を閉じる |
| 401/403、APIキー未設定、400/402/404等の設定・リクエスト障害 | 自動再試行せず追跡済み予約枠を返却。空の正常Cronでも解除しない設定障害のブロックを残す。管理者が設定修復後、サーバー専用clear_analysis_provider_blockを明示実行するまで受付を閉じる |
| 不正な画像入力、読取不能／不正なOCR結果 | 画像・読取結果の失敗として保存し、ワーカーの基盤障害と混同しない。自動再試行しない。この場合の利用枠消費は従来どおり |
| 任意のカタログ補完 | 保存済み・読取済みの寸法を捨てて画像全体を再推論しない。90秒の上限とmaxRetries:0で補完を止め、要確認の補完情報として扱う。既存の最大12ステップは維持 |

Googleの説明では429/503等の一時障害にバックオフと再試行上限が推奨される。導入済み `@google/generative-ai` のmakeRequestには自動再試行がないこともコードで確認した。SDKのHTTP status/errorDetailsを型付きの内部エラーに変換し、生のSDKメッセージ・URL・資格情報を利用者やログへ出さない。[公式の再試行方針](https://ai.google.dev/gemini-api/docs/troubleshooting)

## 永続状態と枠

再試行は同じジョブ・画像・予約を使い、追加の月間枠を消費しない。画像の期限付きリースとトークンを検証してからqueuedへ戻し、recovery_not_beforeまで再取得しない。providerのクールダウン中は新しい画像保存・ジョブ作成・利用者の再開を拒否する。定期回復は止めず、期限後の未完ジョブを確認する。設定障害以外の一時ブロックは期限切れ後に再評価するが、外部サービスの復旧を保証するものではない。

新しい作成RPCは予約月・予約枚数・返却済み枚数・方式reserved-v1を同じ受付トランザクションで記録する。基盤障害で終端failedになった場合、利用可能な合算結果を作れないジョブの予約全体を、その予約月へ一度だけ返す。一部画像の解析が済んでいても、結果・画像IDを削除しない。成功した再試行は予約を一度だけ消費する。管理者と無制限ユーザーは予約0であり、消費・返却の対象にならない。

返却と終端状態は同じDBトランザクションで行い、ジョブ→画像の順にロックする。成功との競合はどちらか一方に確定し、返却後の古いワーカーによる成功は拒否する。返却済み枚数を使うため重複要求でも二度返さない。予約行が見つからない場合は一連の変更をrollbackし、推測の返却はしない。繰り返し中断してリースの3回上限に達した新規ジョブも基盤障害として返却する。

過去ジョブの予約条件は復元できないため、追加列の既定はlegacy_unknownとし自動返却しない。過去分に返却が必要なら管理者が実際の利用記録と照合する。既存利用者・管理者ID・招待履歴・無制限設定を移行で変えない。

Cronはstatus名だけで成功を判定しない。providerエラーを記録した呼出しは、再試行待ちでも上限停止でも失敗heartbeat・HTTP503になる。providerの受付ブロックは別の非公開表に残り、正常な空呼出し2回だけで認証エラーを解除できない。

## 費用と限界

外部AIにジョブUUIDを渡して重複課金を防げる仕組みは、この実装で確認できていない。応答を得られなかった処理が外部で完了している可能性や、明示5xx後の再試行、実行時間切れ後のリース再取得では、推論料金が重なる可能性が残る。自動の即時連打はせず回数と待ち時間を制限するが、外部料金のexactly-onceは保証しない。アプリの利用枠返却は、外部AIからの料金返金とは別である。

実AIの料金・現在の残高・実画像での認識精度は未検証。Hobbyを維持し、Pro変更や追加固定費を発生させないというユーザー方針を継続する。プラン変更、秘密生成、外部設定、本番適用は行っていない。
