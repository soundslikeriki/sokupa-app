# 通知待ち中も次の解析を開始する修正

独立レビューcdbf5c1の「解析done・通知failedで新規解析がロックされる」を修正。本番は未変更。招待、既存LINE ID、admin無制限、DB／Storage権限、署名認証、画像計算、閉画面Cronは変更しない。

## 状態の分離

- 解析受付ロックはqueued／runningだけに使う。doneと判明したら、結果取得を再試行している場合も新しい解析を開始できる。結果を取得できたら、結果の適用または下書きとの競合確認を行う。通知pending／failedを理由にロックを残さない。
- 通知はjob IDごとの独立した監視へ引き継ぐ。GETによる状態確認は5秒間隔、通知の再開要求は各ジョブで30秒以上空ける。HTTP202後に通知が失敗した場合、503、取得失敗のいずれも監視を終わらせない。
- 通知監視は結果・現場名・下書き・解析のactive jobを変更しない。通知Aが後からacceptedになっても、新解析Bの進行を解除したり、結果Aを再適用したりしない。
- lastJobIdは削除対象IDと一致する場合に限って削除する。Aの通知完了がBの保存IDを消さない。新しい明示操作の後に古い初期復元要求が戻っても、選んだ解析を置換しない。
- 既読のdoneジョブが通知待ちとして一覧へ戻った場合は、通知監視だけに使う。結果未確認、queued／running、保存結果がない場合の明示ポインターは別途復元する。

通知状態はDBに保持される。再読込時は本人専用一覧から通知待ちを再発見し、解析中Bのポインターを復元しても通知Aを監視する。一覧には既存のsite_name／notification_statusを追加し、本人専用job取得には既存のclient_result_seen_atも返す。所有者フィルターと署名認証は維持する。新しい表・migration・資格情報は不要。

画面には通知ごとの再確認中／LINE受付済み／要確認を表示する。pending／failedは表示履歴から捨てず、accepted等の終了済み表示だけ直近10件に抑える。DBの履歴は削除しない。acceptedはLINE API受付であり、端末到着保証とは区別する。

## 新解析と下書き

Aの通知が失敗中でも新しい画像をBとして受け付けられる。Aの編集は従来の確認付き退避で保護し、容量不足ならAを残してBの解析を続ける。B完了時に切替方法を選べる。通知監視が切替や退避を実行することはない。

画面を閉じた場合も、従来のprivate permit＋毎分Cronと安定したLINE retry keyで処理・通知を再試行する。23時間超の通知をuncertainにする制限は維持する。今回のUI監視は閉画面処理の前提にはならない。

## 検証と限界

合成APIのブラウザ試験では、202後の通知failed、再開503、状態取得の一時503、A取得がB受付後まで遅れるケースに加え、一覧でdoneと分かっていても結果取得が503となるケースを含める。A失敗中のB受付、A回復中のB進行とポインター保持、B完了時の再受付、A編集の退避、容量不足、B通知待ちでの再読込と新画像準備を確認する。旧来の下書き・別ジョブ選択の回帰も実施する。今回の単体テストは75件、ブラウザは新規32項目＋既存95項目＝127項目が成功し、型検査・lint・本番buildも成功した。証跡summaryとログを添付する。

単体では通知状態のジョブ別merge、古い応答でaccepted等をfailedへ戻さないこと、未完通知を落とさない履歴制限、別ジョブのポインターを消さないこと、通知専用バックログを結果復元しない判定、done／failedでは新規受付をロックしないことを検証する。

実LINE／AIへの送信は行わない。実iPhone・Vercelでの確認と本番保全、最新差分の独立レビュー、既存の秘密／Cron設定の個別承認は引き続き必要。本番公開・課金変更は実施していない。
